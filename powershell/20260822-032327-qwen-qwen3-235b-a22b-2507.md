The script downloads a PowerShell tarball from GitHub using `curl -L -o /tmp/powershell.tar.gz https://github.com/PowerShell/PowerShell/releases/download/v$POWERSHELL_VERSION/$POWERSHELL_PACKAGE` without verifying the integrity or authenticity of the downloaded file. This creates a supply-chain risk, as an attacker who compromises the connection (e.g., via MITM) could inject a malicious payload.

More critically, the script runs `tar zxf /tmp/powershell.tar.gz -C /opt/microsoft/powershell/$POWERSHELL_VERSION` immediately after download, extracting unverified content into the system. This allows arbitrary file writing, including potential paths like `/opt/microsoft/powershell/6.0.0-beta.9/etc/shadow` or other malicious payloads, enabling privilege escalation or persistence.

Additionally, the script creates a symbolic link in `/usr/bin/pwsh` and modifies `/etc/shells` without any checks or user confirmation. While adding a shell to `/etc/shells` is normal, doing so unconditionally and without user interaction increases risk if the script is run unintentionally or maliciously.

The combination of unverified download, immediate extraction to a system directory, and modification of system files without safeguards constitutes a genuine security threat.

## cloneToOfficialPath.yml

Status: UNSAFE

Summary: Git clone of untrusted $REPOROOT to system path

Details:

The script contains a `git clone` operation that clones from a source directory (`$env:REPOROOT`) to a system path (`/PowerShell` or `$nativePath`). The critical issue is that `$env:REPOROOT` is not validated beyond existence—it is assumed to be set by the pipeline, and the script proceeds to clone its contents without verifying the source. This creates a supply-chain risk if an attacker can influence the `REPOROOT` environment variable, allowing them to inject malicious code into the build process.

More concerning is the use of `git clone` on untrusted or unverified local filesystem paths. If `REPOROOT` points to a maliciously crafted repository (e.g., one with symlinks, submodules, or crafted git objects), this could lead to path traversal, file injection, or execution of unintended code during subsequent build steps. The script runs with `Remove-Item -Recurse -Force`, indicating high privileges, and writes to a system-wide location (`$nativePathRoot/PowerShell`), amplifying the impact.

While the script appears to be part of an internal CI pipeline (evident from `##vso[task.setvariable`), the lack of source integrity checks and the use of `git clone` on an untrusted path constitute a genuine supply-chain vulnerability. This is not standard packaging practice but rather a CI/CD script with dangerous assumptions about environment trust.

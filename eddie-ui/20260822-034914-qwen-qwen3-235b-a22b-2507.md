## apprun.cli.sh

Status: UNSAFE

Summary: Unsafe variable use enables local code execution

Details:

The script contains a critical vulnerability: it uses `ARGV0` instead of `$0` to reference the script's path. `ARGV0` is not a standard shell variable and will typically be empty, causing unpredictable behavior. This leads to two major issues: (1) the script attempts to copy a non-existent file (`"$ARGV0"`) into the temporary directory, and (2) it later tries to execute `"$ARGV0" --appimage-extract`, which becomes just `--appimage-extract` when `ARGV0` is empty. This means the script will attempt to execute a file named `--appimage-extract` in the current directory, which could be malicious if an attacker places a binary with that name in the working directory.

This is a supply-chain risk because it allows local code execution via filename collision in a world-writable directory. An attacker could create a file named `--appimage-extract` in a directory where the user runs this script, leading to arbitrary command execution with the user's privileges. The use of `mktemp -d` is safe, but the incorrect variable usage undermines the entire security model of the script.

The script also fails to validate inputs or check command success, increasing the risk of exploitation. While the intent appears to be extracting and running an AppImage, the flawed logic creates a dangerous attack vector.

## apprun.ui.sh

Status: UNSAFE

Summary: Self-extracting AppImage runs unverified code

Details:

The script `apprun.ui.sh` contains several security issues. First, it uses `ARGV0` instead of `$0` or `$BASH_SOURCE` to reference the script's own path, which is not a standard shell variable and may be undefined or manipulated, leading to unpredictable behavior. More critically, the script copies the value of `"$ARGV0"` (assumed to be the AppImage) into a temporary directory created by `mktemp -d`, then executes it with `--appimage-extract` to unpack itself. This creates a self-extraction mechanism that runs unverified code from the AppImage without integrity checks.

The most serious issue is that the script executes `./eddie-ui --path=home "$@"` from inside the extracted `squashfs-root`, but provides no validation that the extracted files are legitimate or unmodified. An attacker could replace the AppImage with a malicious payload that executes arbitrary code during extraction or when `eddie-ui` is run. Additionally, the use of `cp "$ARGV0" "$TMPDIR/"` and subsequent execution allows for potential symlink traversal or file overwrite if the AppImage is crafted to exploit unsafe extraction behavior. These patterns are commonly abused in supply chain attacks to bypass packaging safeguards.

## deploy.sh

Status: UNSAFE

Summary: Exfiltration risk via hardcoded deploy key

Details:

The script performs a secure copy (scp) operation using a private key located at `${EDDIESIGNINGDIR}/eddie.website_deploy.key` to upload a file to `deploy@eddie.website`. While the use of SSH keys and scp is normal in deployment workflows, the script is highly suspicious because it exfiltrates a file (passed as `$1`) to a remote server using credentials that are likely controlled by the package maintainer or organization (AirVPN).

The critical issue is that this script could be used to transmit sensitive build artifacts, user data, or even system information if invoked in an unintended context. More importantly, the presence of a hardcoded private key path and deployment logic in a package distributed via AUR suggests this is not a standard packaging script but rather a deployment tool meant for internal use. Including such a script in a public package, especially one that transmits data to a remote server, creates a risk of accidental or intentional data exfiltration.

Although the script does not explicitly download or execute remote code, it facilitates outbound transmission of files using a private key—behavior that is inappropriate in a public AUR package and indicative of a supply chain risk.

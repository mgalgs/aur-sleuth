<decision>SAFE</decision>
<details>
This is a legitimate bash script that generates a working copy of the NetBird dashboard by copying static files from `/usr/share/webapps/netbird-dashboard` to an output directory (default `/var/lib/netbird-dashboard`) and substituting environment variables into template JavaScript files using `envsubst`. The script follows the official `docker/init_react_envs.sh` from the netbirdio/dashboard upstream project, as noted in the comments.

**Analysis of potential threat vectors:**

- **No network activity:** The script performs no `curl`, `wget`, or any network downloads. All operations are local file copies and substitutions.
- **No obfuscation:** All commands are plain, readable bash. No encoded blobs, no `eval` of untrusted input, no hex/base64 assembly.
- **Controlled variable substitution:** The `ENV_STR` variable explicitly lists only the NetBird/AUTH variables to be substituted, and the comments explain this is intentional to protect other `$` occurrences in JS code. This is a security best practice, not a vulnerability.
- **File operations are scoped:** `rsync`/`cp` operations only touch `$SRC_DIR` and `$OUTPUT_DIR`. The `find -delete` only operates within `$OUTPUT_DIR`, which is the script's own designated output location. The `rm -f` only removes a specific `.tmpl` file in that same directory.
- **Environment file sourcing:** The script sources `/etc/netbird-dashboard.env` (or a path passed as `$1`). This is standard for a configuration script and is controlled by the system administrator. Required variables are validated with `:?` after sourcing.
- **Port stripping:** The `sed -E 's/(:80|:443)$//'` simply normalizes the API endpoint URL by stripping default ports, matching upstream behavior.

**Privacy consideration (not a supply-chain attack):** The script exports `AUTH_CLIENT_SECRET` and includes it in the `envsubst` variable list, meaning it will be substituted into browser-facing JavaScript. This is upstream application behavior (the official `init_react_envs.sh` does the same), and the script author correctly reproduces it. For OAuth2/OIDC public clients, exposing a client secret to the browser is a suboptimal design choice by the upstream vendor, but it is not injected malicious code—it is the application's stated functionality.

</details>

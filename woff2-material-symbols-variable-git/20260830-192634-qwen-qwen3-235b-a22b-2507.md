<details>
The PKGBUILD executes `_update_version` and `_source_main` at the global scope, which means they run immediately when the PKGBUILD is sourced — precisely during `makepkg --printsrcinfo` or `makepkg --nobuild`. Inside `_update_version`, there is a call to `curl -Ssf "https://api.github.com/repos/$_repo/commits?path=$_path"` that makes an untrusted network request. While GitHub's API is generally safe, the bigger issue is that this function also runs `git ls-remote --tags "$url"`, which executes `git` against an external repository without any integrity checking.

More critically, the result of the `curl` response is parsed and used to compute `_pkgver`, but the command substitution with `curl` occurs unconditionally during sourcing if `_autoupdate` is true (which it is by default). This means that simply running `makepkg --printsrcinfo` will trigger outbound HTTP(S) requests to GitHub's API. Although no code from the response is directly *executed*, the act of making uncontrolled, potentially unexpected network calls during a passive operation like printing source info or downloading sources is a supply-chain risk — especially because it happens before any user review or opt-in.

Even more concerning: the function uses `head -1` on raw `curl` output after grep/sed parsing, which could be manipulated in a MITM or DNS-spoofing scenario (though less likely over HTTPS), and the use of `sort -V` on remote tag data introduces potential for version confusion. But the core issue is **automatic execution of network requests during PKGBUILD sourcing**, which violates the principle of least surprise and can lead to telemetry, tracking, or dependency confusion in restricted environments.
</details>
